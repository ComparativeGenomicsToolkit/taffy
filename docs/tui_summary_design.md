# Design: bigMaf / bigMafSummary replacement via the universal `.tui`

Status: **design** (2026-06-20). Author: design recon + synthesis.
Related: [tui_format.md](tui_format.md), [tui_drop_c_index.md](tui_drop_c_index.md), `taf_chain.c` (tui-chain), `taffy/blockViz/`.

## Goal

Replace the UCSC **bigMaf + bigMafSummary** pair (two derived bigBed files per
alignment) with the **universal TAF/`.tui` index** as the single source, queried
at runtime. The genome browser draws a MAF/wiggle-maf track in two regimes,
switched at a window-size threshold (`summaryWindowSize`, default **1 Mb**):

- **Zoomed in (< 1 Mb):** full alignment blocks. UCSC pulls these from the
  bigMaf; **taffy already does this** with `taffy view -U query --noAncestors`
  (benchmarked: 577-way cmp1/cmp5 view benches). Considered solved.
- **Zoomed out (> 1 Mb):** the **bigMafSummary** — per-query-species scored
  coverage bars on the *reference* coordinate. This doc is about replacing
  *this* half from the `.tui`.

### What bigMafSummary stores (the target output)

A flattened bigBed (`bed3+4`, `mafSummary.as`); one row **per non-reference
species per merged block**:

| field | meaning |
|---|---|
| `chrom, chromStart, chromEnd` | reference (hg38) interval, 0-based |
| `src` | the aligned query species/sequence |
| `score` | 0..1 (UCSC: per-base normalized multiz score) |
| `leftStatus, rightStatus` | 1-char synteny/gap codes vs the adjacent same-species block |

Generated by `hgLoadMafSummary` with `mergeGap=500`, `minSize=10000`,
`maxSize=50000` (chop), `minSeqSize=1` (cactus override). **Single
summarization level** — not a zoom pyramid. Status codes: `C` contig (gap 0),
`I` insert (small gap), `N` new/break (gap > 100 kb), `T` tandem (overlap/reverse),
`M` missing (>95% N / assembly gap).

## Key findings (grounded in the code)

1. **The `.tui` stores no score.** Each run carries only
   `(t_start, g_start, length, strand)` (`taffy/inc/tui.h`,
   `taffy/impl/tui.c:651-687`). The chained `.tui` (`taf_chain.c`) merges runs
   within `maxGap` but also attaches no score. `length` *is* the aligned-column
   (match) count, so **coverage is implicit; identity is not recoverable**
   without re-reading bases.
2. **The coverage engine already exists.** `taffyBlockViz` has a tested
   COVERAGE path (`taffy/blockViz/impl/taffyBlockViz.cpp:1399-1513`): above a
   `span/max_output_blocks` bin threshold (`BLOCK_MIN_COARSE_BIN` 10 kb) it bins
   the reference window, picks the dominant block per bin, and groups bins by
   diagonal into per-chain coverage — driven off the **chained `.tui`** via
   `tui_genome_lift_visit_runs` + `taffy_chain`. This *is* "fast liftover over
   chain files." `chainSummary.totalScore` = summed run lengths = aligned bp
   (`taffyBlockViz.cpp:755-765`).
3. **It is not yet per-species summary rows.** blockViz emits reference blocks
   grouped by `chainId` for **one target genome per call**, no `src` row layout,
   no status codes. The recon verdict: a thin query-time wrapper that re-emits
   `(chrom,start,end,src,score,leftStatus,rightStatus)` from the coverage path is
   **possible with no missing pieces**.
4. **Size shaping** is the chained-`.tui` `maxGap` (auto ~1k apes / ~10k 577-way)
   plus blockViz's bin/noise/paralogy filters; `minSize/maxSize` chop is a cheap
   query-time pass.

## Decisions

- **Score = coverage fraction** (not multiz identity). Defined per emitted block
  as `aligned_bp / reference_span` (`totalScore / span`, both already computed by
  the coverage path). **Rationale:** free — no base re-reading, no build-time
  score sidecar, no `.tui` schema change. (Identity would have forced a
  per-run score sidecar built by re-scoring every run — the expensive path we
  avoid.) **Caveat for the demo:** a well-aligned and a poorly-aligned region of
  equal coverage show the same bar height; coverage ≠ UCSC's identity-weighted
  bar. Acceptable; note it on any slide.
- **Integration = runtime query from the `.tui`** (no `.summary.bb` files). The
  browser/CGI calls a taffy entry point per window, mirroring how it already
  calls `halBlockViz` for HAL snakes (taffyBlockViz was built to mirror it).
- **Storage = local (NVMe), assumed (2026-06-20).** Network/object-storage
  support is a separate future effort (touches many places), so the design
  targets local storage — where **forward block-sampling** (seek-bound, cheap
  seeks) is the chosen mechanism. The **universal-coord summary sidecar + realtime
  lift** is the parked fallback for the network-storage future (one contiguous
  read beats 1000 seeks there).

## Design

Build in two layers:

1. **`taffy summary` CLI** (the prototype + test/bench artifact). Input: the
   universal TAF + (chained) `.tui`, a reference window `chrom:start-end`,
   optional species subset. Output: bigMafSummary-equivalent `bed3+4` rows to
   stdout — `chrom start end src score leftStatus rightStatus`. Internally:
   - loop query species (all leaves, or a requested subset);
   - per species, run the **existing blockViz coverage path** over the window
     (chained `.tui`, `tui_genome_lift_visit_runs` + `taffy_chain`);
   - emit one row per merged coverage block, `src = species`,
     `score = aligned_bp / span`;
   - derive `leftStatus/rightStatus` from the gap/strand to the adjacent
     same-species block (see mapping below);
   - apply `minSize/maxSize` chop to match summary visual density.
2. **Library entry point** for the browser CGI (after the CLI is validated):
   the same computation behind a `taffyGet…Summary…` call returning the rows,
   parallelized over species.

### Status-code derivation (query time, from chain geometry)

| condition (vs adjacent same-species block) | code |
|---|---|
| ref gap 0, same strand, collinear | `C` |
| small ref gap, query advances | `I` |
| ref or query gap > 100 kb | `N` |
| query overlaps / reverses (tandem) | `T` |
| gap is assembly-N region | `M` — **not derivable** from the `.tui` (no N-content); approximate or omit |

`M` is the only lossy code (cactus MAFs often have degenerate status anyway).

### Size shaping

Rely on the chained-`.tui` `maxGap` for merge; add an emit-time `minSize`
(buffer-and-merge small blocks) and `maxSize` (chop) pass to mirror
`hgLoadMafSummary` (10k–50k band) for consistent visual density. Possibly a
summary-tuned `maxGap` distinct from the browser-detail chain.

## The make-or-break risk: all-species latency

The runtime path lifts the window to **each** query species. Per-species is fast
(blockViz whole-chrom is sub-second to ~2 s), but **×577 species** at
whole-chromosome zoom may exceed the interactive budget. **De-risk by
prototyping `taffy summary` and measuring it directly** at 1M / 10M /
whole-chrom windows. Mitigations if too slow:
- parallelize per-species lifts (per-genome `TuiGenomeLift` is per-thread-safe);
- cache lift tables (blockViz already does via `get_or_load_gl`);
- compute only requested/visible species;
- last resort: precompute a summary sidecar at build time (reintroduces a
  derived artifact — avoid unless forced).

## Prototype results (2026-06-20)

`taffy summary` (taf_summary.cpp) built as a thin loop over the blockViz coverage
API (`taffyGetBlocksInTargetRange` per query species → group by chainId →
coverage-fraction rows). Measured on real local `.tui`s:

| input | window | species | wall | per-species |
|---|---|---|---|---|
| apes (8-way) base | 1 Mb | 14 | 0.48 s | 34 ms |
| apes base | 10 Mb | 14 | 1.26 s | 90 ms |
| apes chained | whole chr3 (198 Mb) | 14 | 4.07 s | 291 ms |
| **577-way chained g10000** | **1 Mb** | **1152** | **57.5 s** | **50 ms** |

**Conclusion: serial per-species is non-viable.** 57.5 s for the *smallest*
summary window (1 Mb) at 577-way; wider/whole-chrom is far worse. The cost is
fundamental to looping the per-qSpecies API ×1152.

**Levers (in increasing effort / payoff):**
1. **Skip ancestors** — 1152 → 577 (bigMafSummary is leaves only). ~2×. Needs
   the `# hal` tree to classify ancestor vs leaf (not exposed by blockViz today).
2. **Parallelize** — but `taffyGetBlocksInTargetRange` **serializes on a
   per-handle mutex**, so concurrent calls on one handle don't speed up. Real
   parallelism needs **one `taffyOpen` handle per thread** (shared mmap'd `.tui`,
   per-thread lift tables). ÷cores: ~1–2 s for 1 Mb on 32 cores — borderline.
3. **Amortized all-species sweep** (the real fix) — one `tui_query` on the
   reference window + one shared chunk decode, visiting every genome's runs in a
   single pass, instead of 1152 independent lift-table loads + queries. Collapses
   the per-call fixed overhead. Likely needs a new tui/blockViz entry point, not
   the per-qSpecies API.

### All-species sweep results (the follow-up prototype)

`taffy summary --sweep` (low-level tui API: one `tui_query` on the reference
window, then loop genomes doing `tui_genome_lift_load` + `tui_genome_lift_visit_
runs`, accumulating covered columns — no per-species `tui_query`, no chaining, no
blockViz mutex; `-T` parallelizes with one `Tui*` per thread).

- **Serial sweep is *not* faster** than the blockViz loop (70 s vs 57.5 s at
  577-way 1 Mb). Removing `tui_query`/chaining didn't help → those weren't the
  bottleneck.
- **The bottleneck is per-genome lift-table loading** (random I/O into the multi-
  GB `.tui`). Proof: the sweep cost is nearly *window-independent* — 577-way
  all-species took 27.9 s @ 1 kb, 32.3 s @ 1 Mb, 50.7 s @ 10 Mb. The ~28 s floor
  is ~24 ms/genome × 1152 just to load each genome's chunk directory, paid even
  by the 561 species with **zero** coverage in the window.
- **Parallel helps but is I/O-bound** (8-core box): 1 Mb / 1152 species
  33.9 s → 9.4 s at 8 threads (**3.6×**, sub-linear), flat past 8 cores.
  Leaves-only (~577) ≈ half → ~5 s.

**Conclusion: the pure-runtime decision hits a per-genome-I/O wall at 577-way.**
Even fully parallel + leaves-only, the *smallest* summary window is ~5 s on
8 cores (maybe ~1–2 s on a many-core server with fast NVMe, but the sub-linear
scaling says don't count on it). Not interactive. The lever is no longer
algorithmic — it's **data layout**:
- **A compact coverage-summary sidecar** (precompute per-genome coarse coverage
  from the `.tui`, laid out for ONE sequential read of all genomes, not 1152
  random seeks). This is what bigMafSummary fundamentally *is*; the prototype
  shows runtime can't dodge it at 577-way. Still `.tui`-derived, much smaller
  than the `.tui`, and the all-genome single-read kills the random-I/O floor.
- or reorganize the `.tui` for column-major / all-genome access (big format change).

This is the key finding to feed back into the "runtime vs precompute" decision.

### Forward block-sampling — the promising path (`--sample`)

Insight (the browser shows ~1000 px, so we only need ~1000 samples): the
universal MAF/TAF is in column order == file order, and **every block already
carries all species**, so sample ~N columns across the window and read the whole
block at each. Cost scales with **N (pixels), independent of species count** —
the property the reverse-lift floor lacked. We sample at the `.tui` **X-index
anchors** (`column → file-offset`, ~every 10k cols) so each read is a direct
seek, not a scan; conveniently 10k columns ≈ bigMafSummary's own 10 kb `minSize`,
so the anchor grid IS a pixel grid at the display's resolution.

apes results (real MAF, `taffy summary --sample`):

| approach | window | wall | per-block |
|---|---|---|---|
| forward `--sample` | 1 Mb | 0.010 s (93 blocks) | 0.11 ms |
| forward `--sample` | 10 Mb | 0.071 s (957 blocks) | 0.07 ms |
| reverse `--sweep` | 1 Mb | 1.35 s | — |
| reverse `--sweep` | 10 Mb | 0.41 s | — |

Correct: sampled coverage matches the reverse-lift within sampling error
(Anc0 0.944 vs 0.941; hs1 0.999 vs 1.000). **6–130× faster on apes**, and the
gap *widens* with species count since forward is species-independent while
reverse is ∝ species. Headroom: trivially parallelizable, and we currently parse
full blocks but only need row *presence* — skipping bases would cut the per-block
cost hard at 577-way (where bases dominate block bytes).

**577 over sshfs** (local `.tui` for the load via `--maf` to point extraction at
the remote `/mnt/cluster_unitaf/...uni.taf.gz`; X-index offsets matched the real
file): 100 kb window, 9 anchors, 9 blocks → **170 species-rows**, 1.68 s
(187 ms/block). Two readings: (1) a block at this locus is only ~170 rows (just
the species that align there), not ~1150 — so the parse is modest; (2) the
187 ms/block is **sshfs network round-trip latency**, not compute (a local
~170-row block ≈ ~1 ms by the apes 0.07 ms/14-row rate). On the server's LOCAL
storage, ~1–5 ms/block → ~1000 blocks ≈ 1–5 s serial, sub-second parallel.

**Key trade-off this surfaces:** forward-sampling is **seek-bound** (~1000
scattered random reads = round-trips), so it shines on low-latency local storage
and suffers on high-latency network FS. A browser backend on local NVMe → ideal;
on object/network storage → the per-query seeks hurt, and the precomputed
universal-coord summary sidecar (one contiguous read) becomes the better fit.
**So the runtime-sampling-vs-sidecar choice partly hinges on the deployment's
storage latency.** (A true server-local 577 number isn't measurable here — only
the stub + sshfs are available — but the ~170-row block + apes 0.07 ms/block +
seek-bound structure make the case.)

**Alternative direction (user, less preferred):** precompute a bigMafSummary in
*universal* coordinates, then lift it to each genome in realtime. Avoids the
per-query block reads but needs an extra precomputed index (the artifact we hoped
to avoid). Worth holding as a fallback if forward-sampling doesn't scale.

**Secondary findings:**
- Output semantics: grouping by `chainId` emits the chain *bounding box*, so a
  chain with large internal gaps becomes one wide low-score interval (observed:
  a 9.5 Mb span at 0.028 coverage). For faithful summary bars, emit the covered
  sub-intervals / coverage bins, not the bounding box. Score-as-coverage-fraction
  is correct and in [0,1].
- `taffyGetBlocksInTargetRange` returns NULL only on error; "no coverage" comes
  back as an empty list (561/1152 species empty in the 577 1 Mb window) — handled.

### Coverage output (`--bins`) — correct, but exact = full-window

`taffy summary --bins N` is the real bigMafSummary-matching output: forward-
extract every block in the window, attribute each block's reference span (from
its reference row) to the non-ref species present, accumulate into N reference
bins → `bed3+4` per (species, bin) with coverage fraction + adjacent-bin status.

apes 10 Mb, 1000 bins: **0.79 s**, genuine gradient (hs1 median 1.0; a distant
ape median 0.99, min 0.0006). Correct.

**But exact coverage reads the WHOLE window, and at 577 the block count
explodes:** 100 kb → **21,287 blocks** (≈ 1 block / 5 bp — every insertion across
577 genomes splits a block), 535 species, 16.4 s over sshfs. A 10 Mb window is
~100× that. So exact full-window coverage is impractical at 577; the block
explosion makes *any* full-window pass expensive (it's the per-column/per-block
cost the whole design has been dodging).

### Sampled coverage (`--bins N --sampleCols S`) — DONE, pixel-bound

Estimate per-bin coverage by reading a thin **S-column slice at each X-index
anchor** (direct seek, no scan) instead of the full window, then the SAME ratio
accumulator over the sampled blocks (`covered_ref_bp / total_ref_bp` per bin) —
an unbiased estimate, no clipping. Anchors are **strided down to ~N** (the pixel
count), so cost is **∝ pixels, not window size** — the key property. (The anchor
array is genome-wide, ~7M at 577, so the window range is found by binary search;
no per-anchor interval test — gap-column slices just yield ref-less blocks the
accumulator skips.)

Results (apes, local), N=1000:
- **Cost is pixel-bound:** S=64 → 10 Mb 0.14 s, **whole chr3 (198 Mb) 0.66 s**
  (~1000 slices regardless of window). Exact full-window was 0.69 s for *10 Mb*
  alone and would be minutes for whole-chrom.
- **Accuracy** vs exact: mean |coverage error| ~0.03 (deeper S=500, no stride) to
  ~0.047 (aggressive S=64 + stride). ~93% of bins within 0.1. Notably **S barely
  matters — accuracy is anchor-density-limited**, so a small S is fine.
- **Limitation:** sampling misses ~33% of (species,bin) cells — the sparse/low-
  coverage ones between/within sampled slices (they render 0 instead of a tiny
  bar). Tunable by S/stride; acceptable for a zoom-out overview.

577 over sshfs (seek-dominated, not representative of local): 100 kb exact 16.4 s
→ sampled 2.4 s (21× fewer blocks); 1 Mb sampled 18.4 s. On local (~0.1 ms seeks
vs sshfs 187 ms), the ~1000 anchor reads project to **~1–3 s serial, sub-second
parallel** (one Tui+LI per thread — the final lever, not yet built). True local
577 isn't measurable here (stub + sshfs only), but the apes pixel-bound result +
the 577 block-count reduction support it.

`--bins` (no `--sampleCols`) stays as the exact reference to validate against.

### Validation vs the real bigMafSummary

The apes build ships `8-t2t-apes-2023v2.hg38.bigmaf.summary.bb` (cactus
`maf2bigmaf`), queryable with `bigBedToBed` — ground truth. Its `src` = genome
names (match ours), `leftStatus/rightStatus` are EMPTY (cactus MAF has no iRow
status, as predicted), and its `score` is the multiz identity-ish score (NOT
coverage). Binned to a common 10 kb grid over chr3:1–11 Mb:

- **Exact `--bins` vs bigMafSummary:** mean |diff| 0.03–0.07, ours systematically
  ~0.03–0.07 *higher* (coverage ≥ multiz identity; gap grows with divergence —
  biggest for the most distant species). Positive per-bin correlation 0.46–0.78
  (stronger where there's variance; saturated species correlate weakly).
- **Sampled `--sampleCols` vs bigMafSummary:** means track within 0.03–0.09
  (≈ same as exact, same coverage-vs-identity offset), but per-bin correlation is
  noisier (0.17–0.31) — the cost of estimating each bin from one anchor slice.
  Good for the broad coverage picture; fine per-pixel detail is lossy.

This comparison **caught a regression** (the sampled anchor filter had dropped the
reference-present check, collapsing 10 Mb to 59/1000 bins saturated at 1.0; fixed
f97547f). The `.summary.bb` is now a standing ground-truth regression check.
